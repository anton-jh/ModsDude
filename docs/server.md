# Server

The API is one ASP.NET Core process (`ModsDude.Server.Api`) over PostgreSQL and Azure Blob Storage.
Besides the API it hosts the landing page, the account pages, the admin pages, the Hangfire jobs and the ModHub crawler,
and it is its own sign-in provider. How to set it up and
run it is in the [repository README](../README.md).

## How it works

### Endpoints

Each endpoint is one class implementing `IEndpoint`, under `Endpoints/<Feature>/`. It authorizes, uses
`ApplicationDbContext` directly, calls domain methods and returns typed `Results`.

- The class name minus `Endpoint` becomes the route name (`GetModsV1`), which NSwag turns into the client
  method name.
- Endpoints are registered in order of full type name, so the OpenAPI document comes out the same on
  every build.
- `openapi/v1.json` is generated during a build without a running server. It is checked in, and CI fails
  when it is out of date.

Every endpoint declares its authorization:

- Repo-scoped routes use `RequireRepoLevel(Guest|Member|Admin)`.
- Some endpoints check inside the endpoint instead, or as well:
  - deletes that must answer `Ok` on a repeat after the thing is gone (`DeleteRepo`, `KickMember`);
  - the file-link endpoints, whose repo is in the request body;
  - checks that depend on the subject, such as `CreateInvite`, `UpdateMembership`, `RevokeInvite`
    (creator or Admin), `RecordGameActivity` and `CreateRepo` (trusted users only).
- Routes about the caller's own data (user, changes, repo list, activity) need only an authenticated
  user. So do images and ModHub lookups, whose content is public and has no repo in its address.
  Uploading an image also needs the caller to be trusted or a member of some repo.

### Errors

An expected outcome, such as not found, forbidden, conflict or stale, is a typed result carrying a
problem type from `ErrorHandling/Problems.cs`. Each failure the client might need to react to has its
own problem type; the status code is secondary. Problem types carry both `[EnumMember]` and
`[JsonStringEnumMemberName]`, because System.Text.Json ignores the first.

Anything thrown goes through `ApiExceptionHandler`:

| Thrown | Answer |
| --- | --- |
| Unreadable request (`BadHttpRequestException`) | Its own status (400, or 413 when too large), `InvalidRequest` |
| `DomainValidationException` | 400 `InvalidRequest`, logged as a warning |
| Request aborted by the caller | No body, logged at Debug |
| Caller can't be identified | 401 |
| Anything else | 500 `Unexpected`, logged as an error |

Authorization failures are 403. 401 is only for a caller who can't be identified. Request values are
checked at the boundary by `RequestChecks`, which returns typed refusals. Enums are accepted by name only.

### Build match

Every API request carries `X-ModsDude-Build`. `ClientBuildMiddleware` runs before authentication and
answers anything but this server's own build with 412. The client then shows a "please update" overlay.
In Development, a request without the header is let through so Swagger UI works.

Builds are numbered by counting commits on `main`, and the client package version is `0.0.N`.
`GET /health` answers with the build. `GET /download` redirects to that build's installer.

### Authentication and users

The server is its own sign-in provider. Everything for it lives in `Api/Accounts`.

- **Accounts.** ASP.NET Core Identity stores each user's email and password in `UserAccount`, whose ID is
  the user's ID. A deferred foreign key holds every account to its user, and unique indexes hold one
  account per address and per sign-up request.
- **Tokens.** OpenIddict issues them through the authorization code flow with PKCE, for two registered
  clients: the desktop client (a native app, any loopback port) and, in Development, Swagger UI
  (`AccountClients`, brought in line at every startup). Access tokens are signed JWTs that last 10
  minutes and carry only `sub`. Refresh tokens last 30 days, are replaced on every use, and are refused
  once the account can no longer sign in. `/connect/authorize` and `/connect/token` are in
  `ConnectEndpoints`. The API validates tokens with OpenIddict's validation against the local server.
- **Certificates.** Production signs and encrypts tokens with two certificates from the environment
  (`TokenCertificates`), generated by `scripts/new-token-certificates.ps1`. Development uses OpenIddict's
  development certificates.
- **Account pages.** Razor Pages under `/account`: sign in, sign up, check email, confirm email,
  forgot and reset password, and, signed in with Identity's cookie, change password and change email.
  They, the landing page and the admin pages share `Shared/_Theme.cshtml`: the client's palette,
  generated from `Palette.xaml` into `Shared/_Palette.cshtml` by `scripts/web-palette.ps1`, and recipes
  matching the client's buttons, fields, cards, wells and badges. Dark only.
- **Landing page.** A Razor page at `/` with the Download button. It and the account pages draw one card
  on the window (`Shared/_CardLayout.cshtml`). It is down, like `/download`, while a deploy has the API
  stopped.
  Sign-up (`AccountSignUp`) needs a trust code or an invite, checks each code before anything is written,
  and saves the user, the account and every redemption in one transaction. A resubmit with the same
  request ID and password gets the original outcome.
- **Rules.** An email must be confirmed before the account can sign in. Passwords are 12 to 256
  characters, may not contain the email's name or the display name, and are refused when Pwned Passwords
  lists them (the check is skipped, and logged, when that service can't be reached). Five wrong passwords
  lock the account for 15 minutes, wherever a password is asked for. Changing or resetting the password
  revokes every refresh token the account holds, and the account cookie's security stamp is checked on
  every request, so no browser still signed in can get new ones. One address may post to the account pages 10 times a minute and ask for tokens 60 times.
- **Email.** Sent within the request, never as a Hangfire job, so no link is ever stored. Production sends
  through Resend; Development writes each email to `%TEMP%\ModsDude\emails`.
- **Keys.** Data Protection keys, which the account pages' cookies and antiforgery tokens depend on, are
  stored in the database, encrypted with the token encryption certificate in production.
- **Pruning.** `TokenPruningJob` deletes tokens and authorizations that can no longer be used, once they
  are 45 days old.

`UserLoadingMiddleware` runs for `/api` only. It loads the caller named by the token, answers 401
`NotAuthenticated` when no such user exists and 403 `UserBlocked` when they are blocked. A blocked user
still gets tokens, so the client can show why it is refused.

Two more authentication schemes exist:

- **Admin** (basic auth): for the admin pages and the Hangfire dashboard. It answers only on the admin
  port, and the password compare takes fixed time.
- **Deploy** (`Authorization: Deploy <token>`, kept apart from Bearer on purpose): CI uses it for the
  update announcement.

### Blob storage

Three containers hold the files. The API never handles mod or savegame bytes; it issues short-lived
user-delegation SAS links scoped to one blob, and the client transfers directly.

| Container | Address | Notes |
| --- | --- | --- |
| `mods` | `{repoId}/{modId}/{versionId}` | Upload, then register. Registration refuses unless the blob exists and its recorded `sha256` matches |
| `savegames` | `{repoId}/{savegameId}/{contentHash}` | Content addressed. An address that already exists is reported as `AlreadyStored` |
| `mod-images` | `{hash[..2]}/{hash}` | Mod image renditions and avatars: small WebP files, uploaded and streamed through the API, cached by clients for a year |

The client records the file's SHA-256 in blob metadata while uploading, because Azure only computes MD5.
`CreateModUploadLink` tells two cases apart:

- **`FileAlreadyPresent`** (carries the recorded hash): the blob exists but isn't registered yet, so a
  failed import can be retried.
- **`AlreadyRegistered`**: the version is already in the repo.

The user-delegation key is cached for a day. Links are backdated five minutes to allow for clock skew.
Each issued link is recorded as a `FileTransfer` for the traffic statistics. The API authenticates to
Azure with a service principal from environment variables.

Deleting a row that refers to a blob queues the blob for [storage maintenance](#storage-maintenance),
which deletes it later.

Mod and savegame blobs carry a label in their metadata: repo, game, who added the blob and when, and the
mod version's file name or the savegame's name. It is written once, when the blob is first claimed
(registering a mod version, checking in, publishing or restoring a savegame), and identifies a blob after the rows
that referred to it are gone. A savegame blob is shared by every snapshot with those bytes, so its label
describes the savegame and the first check-in. Values are percent-encoded UTF-8, because metadata is
ASCII only, and each is cut short at 512 encoded characters so a label always fits in storage's 8 KiB.
A label storage refuses anyway is left out, and the blob is claimed without it.

### Background jobs

Hangfire stores its state in the application database, in its own `hangfire` schema outside the EF
migrations. The storage maintenance and retention decisions live in pure, tested code; their Hangfire
classes only fetch and carry out. The ModHub crawl's sweep, poll and refresh logic still lives in its Hangfire class.

| Job | When | Does |
| --- | --- | --- |
| `storage-maintenance` | 02:00 UTC, clear of the retention jobs, and from the admin Storage page | Audits storage against the database, labels blobs, deletes queued blobs (see below) |
| `retention-schedule` | 05:00 Stockholm | Dates rows that [retention](domain.md#retention) made eligible, clears dates that no longer apply |
| `retention-delete` | 06:00 Stockholm | Deletes rows that are due and still eligible for the reason they were dated |
| `storage-statistics` | 03:30 UTC | Records stored bytes and blob counts per container and repo, replacing that day's earlier sample. Retried by Hangfire |
| `modhub-crawl` | 19:00 Stockholm | Crawls ModHub (see below) |

### Storage maintenance

The only code that deletes blobs. It deletes what the database has queued.

**The queue** (`BlobDeletionCandidates`, one row per blob) is filled by the database function
`queue_blob_deletion`:

- Delete triggers on `ModVersions`, `SavegameSnapshots` and `ModImageReference`, and an update or delete
  trigger on `Users.AvatarHash`, queue the blob a row referred to. They fire for every statement and
  cascade, including `ExecuteDelete` and deleting a repo or savegame.
- The upload link endpoints and the image upload queue the blob before it is written, so an upload that
  is never registered is collected too.
- The admin Storage page queues blobs chosen by hand, with the ETag the audit saw.

Queuing a blob again moves `QueuedAt` (the database's clock) and bumps `Requeued`, so a run that read the
row before never drops it.

**A run** (`StorageMaintenance`, under a Postgres advisory lock; a second run does nothing):

1. Inspect: the binding, each container's marker, and the account's soft delete setting
   (`StorageGate`).
2. Audit: list every container, then read what the database refers to, and replace
   `StorageAuditFindings` with the unreferenced, unrecognised and missing blobs. A missing name is
   checked again on its own, because a blob registered during the listing looks missing. Referenced mod
   and savegame blobs with no label are labelled from the database.
3. Delete, only if nothing refused: advance the generation, process every queued candidate, advance again.

Each run processes the whole queue. For each candidate it reads the blob, then asks the database whether
anything refers to it, then whether the row was queued again since it was read, and decides
(`BlobDeletionRule`):

- name doesn't parse, no ETag, written less than a day ago, or queued again → keep for a later run;
- an upload's blob that isn't there yet, queued less than a day ago → keep, since the upload may still be
  under way;
- gone, referred to, or changed since an admin chose it → drop from the queue;
- otherwise → delete, conditional on the ETag just read, and record it in `DeletedBlobs` with its size,
  metadata and the time it was deleted. Storage answering that the blob had already gone counts as
  deleted: that is what a retried delete hears when the first answer was lost. Neither the delete nor the
  record is cancelled once started.

A registration, check-in, publish, restore, image set or avatar claims its blob before it commits, and so
does a savegame upload link that reuses a stored blob (`IBlobContainers.ClaimAsync`): it writes the blob's
metadata on the ETag it read, reading again if that fails. Claimed before the run's read, the blob is too
recent to judge; claimed after it, the ETag has moved and the delete fails. A claim that still fails after
three reads answers `FileBusy`. A claim gives the blob a new ETag, which the client's ranged downloads
carry on through (see [Sync](sync.md#executing)).

`DeletedBlobs` lists a deleted blob for 30 days (`DeletedBlobRetentionDays`), or for as long as the
account's soft delete keeps it where that is longer. Nothing is forgotten while the soft delete setting
can't be read.

**A deleted mod version's file** is deleted at once when an upload link is asked for the same version id,
so a fixed build can be uploaded under it (`DeleteReleasedModFileAsync`). It needs the run lock, a gate
that would let a run delete now, and a last run that deleted freely; otherwise the endpoint answers
`FileAwaitingDeletion` and the file waits for the run. A file that has already gone counts as deleted, and
one a registration refers to again answers `AlreadyRegistered`. It skips the minimum age, so it holds a
per-blob advisory lock (`BlobLocks`) that a registration holds from its claim until its commit. It
advances the generation before and after, like a run.

The advisory lock ids are listed in `AdvisoryLockSpaces`.

**The gate** refuses all writes (labels, markers) and deletes when:

- a container's marker names another binding, or none while the container holds blobs;
- a marker is at a generation this database isn't at, or can't be read;
- the binding names another storage account;
- the database has no binding and storage isn't entirely empty.

It also refuses deletes, but not writes, while soft delete is off, keeps blobs for fewer than 14 days,
or can't be read, and while any referenced blob is missing.

**Binding.** `StorageBinding` holds the binding id, the storage account host, a generation and the id of
the advance that reached it. Each container holds a `modsdude-storage-binding` marker blob with the
binding id, generation and advance id as JSON. Every deleting run advances the generation in the database
and in every marker, in two phases (`PendingGeneration`, `PendingAdvanceId`), so a database restored from
a backup, or a second database on the same storage, is behind the markers once the other has advanced,
and refuses. Two copies at the same generation, such as a backup taken since the last advance, look
identical until one of them advances, and the other refuses from then on. A blob the first one deleted
that the other refers to can be undeleted from soft delete. Two copies advancing at once name the same
generation but different advance ids, so neither accepts the other's markers. A run binds storage only
when it is entirely empty, and marks an empty new container. Anything else is bound by hand on the
admin Storage page, which writes a generation past every marker it finds. A marker holding only a GUID,
from before generations, is upgraded when it matches a binding that has never advanced.

A missed run is skipped, not caught up at startup, so a crash loop can't become a delete loop. The
recurring job is not retried.

**Retention** deletion checks the policy again rather than trusting the date, and clears stale dates
before deciding what is due, so both jobs are idempotent. The writes that can make a row ineligible clear
its date right away (`RetentionUpkeep`). Neither job is retried, because a retry would shift what a
deletion date means. A failure in one repo is logged and doesn't stop the others.

### ModHub crawler

`ModsDude.Server.ModHub` reads the Farming Simulator ModHub website, so the FS adapter can offer newer
versions without the game installed (see [Mods](mods.md#remote-sources)). It belongs to the FS adapter,
and only adapter code talks to it.

- It runs daily. A run sweeps every listing if the last full sweep is a week old or unfinished, then polls
  the newest listings, then re-reads the 900 longest-unread mods. That last step is how mods removed from
  ModHub get deleted.
- It waits a second between requests.
- It stops at a listing page it doesn't recognise, or at the fifth unreadable mod page in a row.
- A run is skipped while another is still processing.

Clients look mods up through `LookUpModHubMods`. Downloads come from ModHub directly, not through the
server.

### Change counters

`GET changes` returns one small set of counters: one for the user, and six for each repo they are in
(repo, profiles, savegames, mods, members, activity), plus the current update announcement. Database triggers move the counters. The client polls it every minute
and re-reads only what moved (see [Client](client.md#keeping-data-current)).

The mod list is a change feed. `GET repos/{id}/mods` takes `after`, the last sequence number the client
has seen, and returns the versions changed since, plus tombstones for deleted ones
(`ModVersionDeletions`), in pages of up to 500. Usage
(which profiles pin what) is its own endpoint, because it changes at different times than the versions.

### Admin pages

Razor pages at `/admin`, behind the admin scheme and only on the admin port, which compose binds to
`127.0.0.1:8081`. They lay out like a client page: tabs on the window, a content pane, a card per
section, and tables and expandable rows in inset wells.

| Page | Shows and does |
| --- | --- |
| Overview | Users, storage trend, traffic, backups, largest items |
| Repos | Rename, archive, restore, delete, prune, invites, members and their levels |
| Users | Rename, remove avatar, block and unblock, grant and revoke trust, memberships |
| Trust codes | Issue, change expiry, revoke |
| Storage | Binding, markers and soft delete; run maintenance; bind by hand; unreferenced, missing and unrecognised blobs from the last audit with their labels; choose unreferenced blobs to delete; the queue; deleted blobs |

The Overview shows a notice while blobs are missing or the last maintenance run deleted nothing.

The Hangfire dashboard is at `/admin/jobs`.

### Update announcement

At the start of a CI run on `main`, CI `PUT`s `/deploy/update-announcement`. If the deploy doesn't
succeed, CI `DELETE`s it again. The announcement is held in memory and lapses after 20 minutes. Clients see it through `GET changes` and warn the user that the
server is about to move on.

### Deploys and backups

The operational steps are in the [repository README](../README.md). The design:

- **Ports.** Only Caddy publishes public ports. The API's admin port is published on localhost only.
- **Memory.** Sized for a server with under 1 GB of RAM:
  - each container has a memory limit (API 400 MB, database 256 MB, Caddy 128 MB), and the API's
    garbage collector sizes its heap to its limit;
  - the database runs with `shared_buffers=64MB` and `max_connections=40`, and the API's connection pool
    holds at most 25;
  - the API runs with write-xor-execute off, which saves tens of MB of double-mapped JIT code;
  - the host swaps to zram, then to a 2 GB file, and earlyoom kills the API (which Docker restarts) before
    the host freezes.
- **Deploy order.** `deploy/deploy.sh` checks its preconditions, loads the image, makes sure the backup
  timers, database and Caddy are up, then stops the API, takes a backup, and migrates in one transaction
  from the idempotent migration script. An `EXIT` trap restarts the old build if the stop, backup or
  migration fails. Only then does it start the new build.
- **Migrations.** Production migrates only in `deploy.sh`. Development migrates at startup.
- **CI.** Concurrency groups are never cancelled, so a deploy is never cut off halfway. Releasing is safe
  to re-run.
- **Backups** run hourly, daily and before every deploy:
  - each dump's table of contents is checked before upload;
  - the daily dump is test-restored into a scratch database;
  - backups are uploaded with a create-only SAS;
  - backup status shows on the admin Overview page.

## Decisions

**Endpoints use the DbContext directly.** There are no handler, mediator or repository layers. Queries
shared by several endpoints live in Persistence extension methods or `*Reads` classes beside the
endpoints.

**Typed problem types, not status codes.** The client branches on what went wrong. Two failures that need
different reactions never share a problem type, even when they share a status.

**Exact build match instead of compatibility.** Client and server of one build ship together. Refusing
any other pairing is simpler and safer than keeping old shapes working.

**Sign-up takes a code.** Nobody can create an empty account: signing up needs a trust code or a repo
invite, so every user arrives able to do something and through someone who let them in.

**The API never handles mod or savegame bytes.** Files are large and many. SAS links let clients go
straight to storage, and the API stays small. Images are the exception: they're small, immutable and
fetched in bulk, so streaming them with long cache headers is simpler.

**Record the hash at upload, verify it at registration.** Azure only computes MD5. Recording SHA-256 in
metadata lets registration refuse a mismatch without the server reading the bytes.

**Repo-scoped composite keys.** The repo's content tables (mod versions, profiles, revisions, savegames,
snapshots) have primary keys that start with `RepoId`. A query can't forget to scope by repo, and a pin
or snapshot can't refer to another repo's rows.

**Blobs are deleted only when the database says so.** Deciding by absence turns a wrong, reset or
restored database into an empty storage account. Queuing on delete means such a database deletes nothing,
or only its own queued blobs, and the gate refuses it anyway. Soft delete on the account makes every
delete recoverable for its retention period.

**Storage maintenance and retention are built to be run by an attacker.** Anyone with dashboard access can
trigger them repeatedly or concurrently. Every run re-derives its decisions from the current data, deletes
conditionally, and refuses to delete at all when storage looks like it belongs to another database.

**The crawler is a guest on someone else's site.** It is slow and polite, stops on anything unexpected,
and is scoped to the one game module that needs it.

**The OpenAPI document is checked in.** It shows API changes in review and lets the client be regenerated
without running the server.

**Migrate while the API is stopped, after a backup.** A failed migration then leaves a database the old
build can still run against, plus a backup taken just before.
